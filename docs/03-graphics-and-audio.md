# 03 — Graphics & Audio (from nothing but code)

> Open the project folder. Notice what isn't there: no `.png` sprites, no `.wav` sound
> effects, no `.mp3` music. Yet the game has pixel-art characters, animated combat, a
> gunshot for every weapon, and an ambient wind-and-drone soundtrack. **Every pixel and
> every sound is generated by math at load time.** This chapter is how — and why that's
> a genuinely useful thing to understand even if you never make a game.

---

## Part 1 — Graphics: drawing pixels with code

### The Canvas: a programmable sheet of graph paper

The browser gives us `<canvas>`, a rectangle of pixels you draw on with JavaScript. The
whole game world renders onto one canvas defined in [`index.html`](../index.html):

```html
<canvas id="game-canvas" width="480" height="320"></canvas>
```

That's a **480×320 grid of pixels**. Small on purpose — it's a *low-resolution* canvas
that CSS then stretches up to fill the screen. This is the secret to the crisp
pixel-art look. Two settings make it work:

```css
#game-canvas { image-rendering: pixelated; }   /* CSS: scale up with hard edges, no blur */
```
```js
ctx.imageSmoothingEnabled = false;             /* JS: don't blur when drawing images */
```

Without these, scaling a 16×16 sprite up to 60×60 would blur it into mush. With them,
each original pixel becomes a crisp block. **We draw tiny and display big.** That single
idea is why the art looks intentionally retro instead of accidentally low-quality.

### Turning text into sprites

Here's the trick that makes hand-drawing sprites in code bearable. In
[`sprites.js`](../js/sprites.js), the `px()` function reads a sprite as **ASCII art** —
a list of strings where each character is a pixel — plus a palette that maps characters
to colors:

```js
function px(rows, pal, w) {
  const c = cnv(width, rows.length);
  const ctx = c.getContext('2d');
  rows.forEach((row, y) => {
    for (let x = 0; x < row.length; x++) {
      const col = pal[row[x]];             // look up this character's color
      if (col) { ctx.fillStyle = col; ctx.fillRect(x, y, 1, 1); }  // paint one pixel
    }
  });
  return c;                                // hand back a ready-to-use mini-canvas
}
```

So a medkit icon is *literally drawn in the source code* as a picture you can see:

```js
store.icon_medkit = px([
  '................',
  '...oooooooooo...',
  '..oWWWWWWWWWWo..',
  '..oWWWWRRWWWWo..',   //  o = outline, W = white, R = red
  '..oWWWWRRWWWWo..',
  '..oWWRRRRRRWWo..',   //  the red cross emerges from the letters
  '..oWWRRRRRRWWo..',
  '..oWWWWRRWWWWo..',
  '..oWWWWRRWWWWo..',
  '..oWWWWWWWWWWo..',
  '...oooooooooo...'
], { o:'#17130e', W:'#d8d5c8', R:'#b3372e' });
```

You can *read the picture in the code.* This is a beautiful example of choosing a
**representation that fits the human**, not just the machine. The computer would be
equally happy with an array of numbers; a person editing the art would not. Picking
data formats that humans can read and edit is a real, underrated engineering skill.

Each sprite is rendered onto its own small off-screen `<canvas>` once, at startup, and
stored in a lookup table (`store['icon_medkit']`). During the game we just `drawImage`
those pre-made canvases — fast, because the drawing-from-strings work happened once.
This is **caching / precomputation**: do expensive work once up front, reuse the result
cheaply forever. (`toURL()` even converts a sprite to a data-URL so the HTML `<img>`
tags in the shop and inventory can display the same generated art.)

### One character, eight animations, from six pictures

Drawing every direction and frame of every character by hand would be brutal. Instead,
the code is lazy in the smart way. `buildHuman()` defines a character in just a few
poses (`down`, `up`, `side`, each with two walk frames) and then **generates the rest**:

```js
if (dir === 'side') {
  store[`${name}_right_${f}`] = c;
  store[`${name}_left_${f}`]  = flipH(c);   // left is just right, mirrored
}
```

`flipH()` mirrors a canvas horizontally, so "walking left" is free — it's "walking
right" flipped. And every character class (Survivalist, Raider, etc.) reuses the *same
body shape* with a different color palette:

```js
buildHuman('player_survivalist', { J:'#6b5a3a', K:'#52432a', h:'#4a3b28' });  // jacket/shade/hair
buildHuman('player_raider',      { J:'#7a3b2e', K:'#5c2a20', h:'#2e2a26' });
```

One template, many skins. This is **Don't Repeat Yourself (DRY)** in art form: define
the shape once, vary only what differs (the colors). When you catch yourself about to
copy-paste-and-tweak, ask instead: *what's the template, and what's the parameter?*

### Procedural tiles and the seeded random number generator

The world is built from tiles — grass, cracked road, rubble, pines. If every grass
tile were identical, the ground would look like graph paper. So tiles have **variants**
with randomly sprinkled specks and blades of grass. But here's the problem: if we used
plain `Math.random()`, the world would look *different every single frame*, shimmering
like TV static.

The fix is a **seeded pseudo-random number generator** — `mulberry32`:

```js
function mulberry32(a) {
  return function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;   // a number in [0, 1)
  };
}
```

You don't need to follow the bit-twiddling. What matters is the *property*: given the
same starting **seed** number, it produces the exact same sequence of "random" numbers
every time. So:

```js
const rng = mulberry32(101);   // seed 101 → always the same wasteland
```

The wasteland is randomly generated, but it's the *same* random wasteland on every
load, because it's built from a fixed seed. This is the concept behind Minecraft world
seeds, procedural game levels, and — importantly — **reproducibility** in serious
software. A "random" test that uses a seeded RNG fails the same way every time, so you
can actually debug it. *Controlled* randomness — random-looking but repeatable — is
one of the most useful tools you can have.

> **Real distinction to carry:** `Math.random()` is for things that should differ every
> time (falling ash, damage rolls). A *seeded* RNG is for things that should look
> varied but stay *stable* (the map). Choosing which kind of randomness you want is a
> real decision, and mixing them up is a classic bug.

### Scenes: gradients, silhouettes, and layered depth

The bigger backdrops — the title skyline, combat arenas, the intro's mushroom cloud —
are painted with gradients and simple shapes, layered back to front like stage
scenery. `drawBackdrop()` for the sunset "wastes," for instance:

1. a vertical **gradient** for the sick orange sky,
2. a low sun,
3. a **silhouette skyline** of broken buildings (generated with a seeded rng so it's
   stable),
4. dead trees in front,
5. a dark ground band,
6. and finally **ash motes** sprinkled on top.

Each layer is just rectangles and gradients, but stacked in the right order they read
as a place with depth. That "background → midground → foreground, drawn in that order"
is the painter's algorithm again (you met it in chapter 2 for sprites) — the same idea
that makes the whole thing feel three-dimensional on a flat canvas.

### Lighting: darkness as a layer you subtract from

The dark maps (woods, factory interior) do something clever with **compositing**. To
make a pool of light around the player, the code covers the screen in near-black, then
*erases a soft circle* out of that darkness where the player stands:

```js
d.fillStyle = 'rgba(2, 4, 8, 0.93)';
d.fillRect(0, 0, VIEW_W, VIEW_H);              // 1. cover everything in dark

const g = d.createRadialGradient(px, py, r*0.2, px, py, r);  // 2. a soft circle
g.addColorStop(0, 'rgba(0,0,0,1)');            //    solid in the middle...
g.addColorStop(1, 'rgba(0,0,0,0)');            //    ...fading to nothing at the edge

d.globalCompositeOperation = 'destination-out'; // 3. "erase" mode
d.fillStyle = g;
d.fillRect(0, 0, VIEW_W, VIEW_H);              //    punch the light-hole in the dark
```

`destination-out` means "wherever I paint, *remove* what's already there." So painting
the gradient doesn't add light — it deletes darkness, leaving a soft-edged window onto
the world. Carrying a lighter simply makes the erased radius bigger (`r = 95` vs `48`).
**Compositing modes** — rules for how new paint combines with existing paint — are a
whole toolbox; this is one small, striking use of them.

## Part 2 — Audio: sound as pure math

There isn't a single sound file. Every effect is **synthesized** — built from raw
waveforms — using the **Web Audio API** in [`audio.js`](../js/audio.js). To get why
that's possible, you need one idea: **sound is just a wiggling number over time.** A
speaker cone pushed in and out fast makes sound; describe the push-and-pull as numbers
and you've described a sound.

### The two atoms: tones and noise

Almost every effect in the game is built from two primitive generators.

**A tone** is a pure pitch — a smooth oscillating wave at some frequency:

```js
function tone(freq, dur, { type = 'square', vol = 0.2, slideTo = null } = {}) {
  const osc = ctx.createOscillator();   // a wave generator
  const g = ctx.createGain();           // a volume knob
  osc.type = type;                      // square / sawtooth / triangle / sine
  osc.frequency.setValueAtTime(freq, t);
  if (slideTo) osc.frequency.exponentialRampToValueAtTime(slideTo, t + dur); // pitch slide
  g.gain.linearRampToValueAtTime(vol, t + 0.008);        // quick fade-in (attack)
  g.gain.exponentialRampToValueAtTime(0.0001, t + dur);  // fade-out (decay)
  osc.connect(g).connect(master);
  osc.start(t); osc.stop(t + dur + 0.05);
}
```

Two things to notice. First, the **waveform type** changes the character: a `square`
wave sounds retro and buzzy (classic 8-bit), a `triangle` softer, a `sawtooth` harsh.
Second, that **envelope** — the quick fade-in then fade-out on the gain (volume) — is
what makes a note sound like a *pluck* or *beep* instead of an ugly click. Real
instruments have this "attack and decay" shape; faking it is what makes synth sounds
feel like sounds.

**Noise** is the opposite — all frequencies at once, like static or wind. It's made
once as two seconds of random samples and reused:

```js
const d = noiseBuf.getChannelData(0);
for (let i = 0; i < len; i++) d[i] = Math.random() * 2 - 1;  // random values in [-1, 1] = hiss
```

Then a **filter** shapes that hiss into something specific — a low rumble, a sharp
"tss," wind — by only letting certain frequencies through. Noise + filter is the
backbone of every percussive and textural sound in the game.

### Building recognizable effects from the atoms

Now the fun part: combine tones and noise and you get *characterful* sounds. Each
weapon fires differently, and you can read the sound design right in the code:

```js
fire(kind) {
  switch (kind) {
    case 'rifle':                                    // one sharp crack
      noise(0.28, { vol: 0.4, freq: 2200, slideTo: 150 });  // bright burst dropping fast
      tone(120, 0.2, { type: 'sawtooth', slideTo: 50 });    // low thump underneath
      break;
    case 'shotgun':                                  // bigger, boomier
      noise(0.4, { vol: 0.5, freq: 1400, slideTo: 90 });
      tone(90, 0.3, { type: 'sawtooth', slideTo: 40 });
      break;
    case 'smg':                                      // three fast pops
      for (let i = 0; i < 3; i++)
        noise(0.09, { vol: 0.3, freq: 1900, delay: i * 0.09 });  // staggered in time
      break;
  }
}
```

A gunshot = a bright filtered-noise burst (the crack) layered over a low sawtooth thump
(the punch), with the pitch sliding *down* fast to mimic the report dying. The SMG is
literally a `for` loop firing three quiet cracks 90ms apart. **You are composing sound
the way you'd compose a function** — small parts, combined and timed. Once you see
that a "gunshot" is just "noise burst + low thump, pitch falling," synthesis stops
being mysterious.

### The soundtrack: layers that never repeat

The ambient music isn't a looping track — it's **three generated layers** running
together, so it never audibly repeats:

1. **Wind** — filtered noise whose filter frequency is slowly swept up and down by a
   very slow oscillator (an **LFO**, low-frequency oscillator), so it breathes.
2. **A drone** — two low triangle waves tuned *slightly* apart (55 and 55.6 Hz). That
   tiny mismatch makes them slowly "beat" against each other, a shimmering detuned
   pad. Deliberate imperfection sounding better than perfection.
3. **Sparse melody notes** — every couple of seconds, *maybe* (35% of the time it stays
   silent) a single note from a minor scale, fed through an **echo** (a delay line with
   feedback) so each note repeats and fades into the cold.

```js
const SCALE = [73.42, 87.31, 98.0, 110.0, 130.81, 146.83]; // a bleak minor scale
melodyTimer = setInterval(() => {
  if (muted || Math.random() < 0.35) return;   // sometimes play nothing — space is part of it
  const f = SCALE[Math.floor(Math.random() * SCALE.length)];
  // ...play a soft triangle note through the echo...
}, 2600);
```

Because pitches are *chosen* from a scale but *timed* by chance, the result is always
musical but never the same twice — endless, non-repeating, and a few kilobytes of code
instead of a multi-megabyte audio file. Generative music from a scale plus randomness
is a lovely little demonstration of **constraints + chance = something that feels
composed.**

### One volume knob to rule them all: the master gain

Every sound connects through a single `master` gain node before reaching the speakers:

```js
osc.connect(g).connect(master);   // every effect routes through `master`
master.connect(ctx.destination);  // master → speakers
```

That's why muting is one line — turn down `master` and *everything* goes quiet at once,
no matter how many sounds are playing:

```js
function toggleMute() { muted = !muted; master.gain.value = muted ? 0 : 0.5; }
```

This is a **single point of control**, and it's the audio version of a system-design
principle you'll use forever: route related things through one chokepoint so you can
control them all at once. (It's the same reason apps funnel every network call through
one client, or every log line through one logger — control the flow at one place.)

## Why generate assets instead of loading files?

It's worth being honest about the trade-off, because "generate everything" is *not*
always the right call.

**What it buys you here:**
- **Zero external files** → the whole game is a handful of tiny text files. Loads
  instantly, works offline, nothing to 404.
- **Everything is version-controlled and diffable.** A change to the art shows up as a
  code diff you can review, not an opaque binary blob.
- **Infinitely tweakable.** Want the rifle punchier? Change a number. No art tool, no
  re-export.

**What it costs:**
- **A real artist is faster in a real art tool.** Hand-drawing a 24×24 bear in ASCII is
  slower than painting it in Aseprite for someone skilled.
- **There's a ceiling on detail.** This approach shines for stylized pixel art; it
  would be absurd for photorealistic graphics or orchestral music.

So the rule isn't "always generate." It's the same calibration lesson from chapter 1:
**match the technique to the project.** For a small, stylized, dependency-free game made
by one person who's also learning, generating everything is a fantastic fit — and it
happens to teach you how pixels and sound *actually work* underneath the tools, which
is knowledge the tools normally hide from you.
